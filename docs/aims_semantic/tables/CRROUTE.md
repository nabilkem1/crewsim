# CRROUTE  (Table)  - Crew pairing (trip / crew route) header: one row per dated pairing instance

## 1. Purpose & business meaning

**What a row is.** The *header of a crew pairing instance* - a named, dated trip such as `C0290` operating on a given day. A pairing (a.k.a. "trip", "crew route", "rotation", "duty pattern") is the unit that crew planners build, publish, bid on and assign to crew members: a start date, a name, the required crew complement per position, categories (augmented crew, training, VIP ...), a date span, and flags. The legs of the pairing are in `CREWLEG` (flights and ground activities); the crew members actually assigned are in `ROSTER`; the hotels in `HOTAC`.

**Grain.** One row per `(CDATE, CROUTE)` - the **pairing key**. `CDATE` is the pairing's **start date** (day number), `CROUTE` is a large numeric id of the **pairing pattern**: the same CROUTE (and the same name `DESC_`) recurs on many CDATEs when the trip operates repeatedly. So `CRROUTE` rows are *instances*; `CROUTE` / `DESC_` identify the *pattern*. Across the entire history, `CROUTE` and `DESC_` are 1:1 (44,201 distinct of each; no CROUTE has two names, no name two CROUTEs), and `(CDATE, DESC_)` is unique, so *"pairing name + start date"* resolves to exactly one instance - which is how the planner-assist procedures look pairings up (`WHERE DESC_ = @PAIRING_ID AND CDATE = DATEDIFF(DAY,'1980-01-01',@date)`).

**Lifecycle.** Created by the crew-pairing module (or auto-generated by the pairing optimiser: `AUTOGENER` = 1 on 75% of 2026 rows); published for crew bidding/assignment; kept as history (2002-2026). CDATE reaches 2026-12-21 at extraction, i.e. pairings are built about 7 weeks ahead. Date range, `ACTUALBEGDATE` / `ACTUALENDDATE`, are updated when flights are re-timed after publication.

**Who reads it (planner-assist).** Every procedure that is addressed by pairing name:
- R0 (draft list), R1, R2 (via `Get_Detailed_Pairing`), R3, R4, R5: resolve `PAIRING_ID` (+ date) to `(CDATE, CROUTE)`, produce `PAIRING_NOT_FOUND` errors with "dates it operates within 30 days", and attach the pairing name (`Trip_Number`) to roster rows via `ROSTER.(DUTYDAY, DUTYNO)`.
- `rpt.Get_Detailed_Pairing`: also decodes the **required crew complement** (`CREWNUM`) and **route categories** (`RTECAT`).
- `rpt.usp_GetPairingID`: pairing name from a flight.

## 4. Keys & relationships

**Natural key / PK**: pairing key `(CDATE, CROUTE)`; alternate unique key `(CDATE, DESC_)` (measured, not declared). `CROUTE <-> DESC_` is 1:1 across all dates.

| To | Cardinality | Exact join predicate (from code) | Source |
|---|---|---|---|
| CREWLEG | 1 : N (one row per leg of the pairing, flights and ground activities) | `cl.CDATE = cro.CDATE AND cl.CROUTE = cro.CROUTE` ; `INNER JOIN TSC.[dbo].[CRROUTE] cr ON cl.CDATE = cr.CDATE AND cl.CROUTE = cr.CROUTE` | R0 195, R3 36/178, R4 224, R5 244, usp_GetPairingID |
| CRLEGGROUND | 1 : N (ground legs only) | `clg.CDATE = cro.CDATE AND clg.CROUTE = cro.CROUTE` (implied; the code joins from CREWLEG/ROSTER with `clg.CDATE = cl.CDATE AND clg.CROUTE = cl.CROUTE`) | R0/R3/R4 |
| ROSTER (documented by someone else) | 1 : N (one row per crew member and leg) | `cro.CDATE = r.DUTYDAY AND cro.CROUTE = r.DUTYNO` (`rpt.usp_GetPairingID`: `fr.CDATE = r.DUTYDAY AND fr.CROUTE = r.DUTYNO`); filters typically add `r.DUTYNO > 0` (negative = stand-alone activity). Measured: 1,398 of 1,398 distinct roster duties with `DUTYNO > 0` on days 17000-17010 exist in CRROUTE. | R0 149 and 680, R3 30/149/160, R4 193/206, R4_Get_Future_Impact 60, R5 216/228/455, CalculateCrewFTC 237 |
| LEGMAIN (flight legs) | N : M via CREWLEG | `CRROUTE -> CREWLEG (CDATE, CROUTE) -> LEGMAIN (DAY, DEP, CARRIER, FLT, LEGCD)` | Get_Detailed_Pairing |
| HOTAC (hotel nights) | 1 : N | `HOTAC.CDATE = CDATE AND HOTAC.CROUTE = CROUTE` (also `h.CHECKINDAY = @TargetCDate AND h.CROUTE = @TargetCRoute`) | Get_Detailed_Pairing |
| vvPositions | positional | byte k of CREWNUM <-> `vvPositions.ID = k` | Get_Detailed_Pairing |
| GENCAT | bit mask | RTECAT bit N <-> `GENCAT.GENCATTYPE = 1 AND GENCATINDEX = N` | Get_Detailed_Pairing |

**How the two keys relate (summary).**
- *Flight key* `(DAY, DEP, CARRIER, FLT, LEGCD)` identifies a flight leg (LEGMAIN/LEGTIMES/CREWLEG/ROSTER.LEG_*).
- *Pairing key* `(CDATE, CROUTE)` identifies a pairing instance (CRROUTE/CREWLEG/CRLEGGROUND/ROSTER.DUTY*).
- CREWLEG carries **both** and so links them (N : M: a pairing has several legs; a leg is in several pairings, one per crew group).
- ROSTER carries both as well and adds the person; a ROSTER row is "crew X, position POS, on flight leg F, within pairing P".

## 5. Encoding conventions & gotchas

- **CDATE is a day number** (days since 1980-01-01) = pairing start date, UTC based; it is NOT the date of every leg. Use `DATEDIFF(DAY,'1980-01-01', @date)` to compare. `DATEADD(DAY, CDATE, '1980-01-01')` to display.
- **Pairing name reuse.** The name (DESC_) recurs on many CDATEs (in 2026: 6,962 patterns over 36,248 instances; 4,453 patterns operate on more than one date, up to 666 dates over the history). Never partition by name when you mean one trip occurrence - use `(CDATE, CROUTE)` (R3 note about `Max_Pairing_TZ_Diff` was fixed for exactly this reason).
- **Name lookups are case-insensitive** and the column is nchar(5) (trailing blanks ignored); use `RTRIM(DESC_)` when concatenating (R3 does `RTRIM(cro.DESC_)`).
- **Pairing must exist on the date.** A name that exists but not on the requested date is a separate error (`PAIRING_NOT_FOUND ... does not operate on ...`) listing other CDATEs within +/- 30 days; the check is `WHERE DESC_ = @id AND CDATE = DATEDIFF(DAY, @BaseDate, @date)`.
- **Pairing with no crew has no ROSTER rows** but still has CRROUTE + CREWLEG rows; do not infer "does not exist" from empty ROSTER.
- **Multi-day pairings**: `ENDDATE - CDATE + 1` days; ROSTER.DUTYDAY is still CDATE for later days.
- **ACTUALBEGDATE / ACTUALENDDATE** drift from CDATE / ENDDATE on ~1-3% of rows because of re-timed flights - but all joins in the code use `CDATE`.
- **CREWNUM is binary**: decode with `CONVERT(TINYINT, SUBSTRING(CREWNUM, k, 1))`; comparing it as text gives garbage; do not apply string functions without a cast.
- **RTECAT sign**: bit 31 gives a negative int (-2147483648 = category 32 "HRS & CREDITS ONLY").
- **Mostly-zero columns**: more than 20 of 34 columns are constant 0/blank in 2026; they are legacy / unused features.
- **Time horizon**: future pairings exist up to the end of 2026; history is complete since 2002.

## 7. Typical query patterns

```sql
-- 1. Resolve a pairing name + date to its key and header attributes
SELECT CDATE, CROUTE, DESC_,
       DATEADD(DAY, CDATE, '1980-01-01')   AS start_date,
       DATEADD(DAY, ENDDATE, '1980-01-01') AS end_date,
       ENDDATE - CDATE + 1                 AS length_days,
       AUTOGENER, RTECAT
FROM TSC.dbo.CRROUTE
WHERE DESC_ = 'C0290' AND CDATE = DATEDIFF(DAY, '1980-01-01', '2026-11-10');

-- 2. Pairings starting in a date window with required pilots / cabin complement decoded
SELECT DESC_, CDATE,
       CONVERT(tinyint, SUBSTRING(CREWNUM,1,1)) AS req_CM,
       CONVERT(tinyint, SUBSTRING(CREWNUM,2,1)) AS req_PO,
       CONVERT(tinyint, SUBSTRING(CREWNUM,5,1)) AS req_DV,
       CONVERT(tinyint, SUBSTRING(CREWNUM,7,1)) AS req_AB
FROM TSC.dbo.CRROUTE
WHERE CDATE BETWEEN DATEDIFF(DAY,'1980-01-01','2026-11-10') AND DATEDIFF(DAY,'1980-01-01','2026-11-16');

-- 3. Dates on which a pairing operates (pattern calendar)
SELECT CONVERT(varchar(10), DATEADD(DAY, CDATE, '1980-01-01'), 23) AS operates_on, ENDDATE - CDATE + 1 AS days
FROM TSC.dbo.CRROUTE
WHERE DESC_ = 'C0290' AND CDATE BETWEEN 17080 AND 17170
ORDER BY CDATE;

-- 4. Pairings flagged "Formation" (route category bit 7) next week
SELECT DESC_, CDATE FROM TSC.dbo.CRROUTE
WHERE CDATE BETWEEN 17108 AND 17115 AND (RTECAT & 64) = 64;

-- 5. Crew assigned to a pairing (join to ROSTER through the pairing key; crew ids only)
SELECT r.ID AS crew_id, r.POS, COUNT(*) AS legs
FROM TSC.dbo.CRROUTE cro
JOIN TSC.dbo.ROSTER r ON r.DUTYDAY = cro.CDATE AND r.DUTYNO = cro.CROUTE
WHERE cro.DESC_ = 'C0290' AND cro.CDATE = DATEDIFF(DAY,'1980-01-01','2026-11-10')
GROUP BY r.ID, r.POS;
```

- **High**: key semantics (CDATE = start day, CROUTE = pattern id, together = instance), name <-> CROUTE 1:1, how it joins ROSTER and CREWLEG, ENDDATE = last arrival day, CREWNUM byte-per-position decode and RTECAT bit decode (both executed by `rpt.Get_Detailed_Pairing`).
- **Medium (inference)**: AUTOGENER = optimiser-generated; name prefix = crew group family (derived from CREWNUM profile); ACTUALBEGDATE / ACTUALENDDATE = as-flown re-timed dates; LANGTBL = language requirement entries.
- **Unknown / unused**: CFLAGS bits, REPFLAG, RULESET, the 20+ zero columns (named-based guesses only), the meaning of S-prefix (training/special) families, why some pairings have an all-zero CREWNUM, why AB can be 34 on a single F pairing (likely a charter/transport special).
- The relation between a pairing and *which crew group it is for* is not stored as a column: it must be derived from CREWNUM (which positions are required) or from the roster positions (`ROSTER.POS`), not from CREWCAT (unused).
