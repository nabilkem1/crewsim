Executive summary — top 5 risks to result validity

The codebase is unusually honest about its own limits — the backlog records real defects, gates were rewritten when they were found to validate stubs, and deliberate deviations carry recorded decisions. The five risks below are the ones that survive that honesty: each was confirmed by executing code in this audit, each silently moves reported numbers, and none is currently caught by any gate.

  1. FIXED The measurement-window attribution rule (des.rows_in_measurement_window) drops every cancellation and terminal penalty whose first ledger row books during cool-down, so E[C], CVaR₉₅ and uncovered-legs systematically omit exactly the failure costs that justify reserves — biasing the recommendation toward fewer reserves. (AUD-03) Every item now books a $0 OPEN_ITEM causal marker at creation — the reproduced $25,700 dropped chain now attributes in full.
  2. FIXED A sick crew member is never marked unavailable: they remain a legal tier-1 draft candidate for the whole absence and can be selected to cover the very pairing their own sickness broke — overstating recovery capacity in every scenario. (AUD-02) An occupying ABSENCE block now spans the absence; the reproduction's selector returns no candidate.
  3. FIXED The calendar interval query CrewMember.blocks_in misses blocks that overlap the query once the engine has created overlapping blocks (which every draft does), so L0, L5, tier pricing and eligibility can silently pass checks they should fail — drafting a pilot mid-mandatory-rest was reproduced. (AUD-01) Exact interval scan; hypothesis property test proves equality with the naive filter on arbitrary overlapping calendars; the mid-rest draft is now ILLEGAL_L0.

S1 — silently wrong numbers

AUD-01 S1 CONFIRMED blocks_in misses overlapping blocks, so legality and tier checks read a partial calendar

Outcome
FIXED blocks_in is now an exact interval scan (state.py); the mid-rest draft repro returns LEGAL ILLEGAL_L0 and the vacation-tier repro returns tier 1 tier 4. Locked by a hypothesis property test (equality with the naive overlap filter on arbitrary overlapping calendars).
Location
src/crewsim/engine/state.py:86–110; consumers: legality.py:28–40 (L0), :207–269 (L5), drafting.py:20–32 (tier), eligibility.py:62–76 (pool)
Evidence
blocks_in bisects on start and checks only index idx−1 for a block spanning the query start — its own comment says "blocks don't overlap … in a valid calendar". But the engine creates overlapping blocks by design: a draft adds DRAFTED_DUTY+REST without consuming the underlying DAY_OFF (documented as intended in find_l0_violations). Reproduced in this audit: crew with REST d0 23:00→d1 10:00 and DAY_OFF d1 00:00→23:59; blocks_in(d1 05:00, 08:00) returns only DAY_OFF, and check_l0_single_assignment approves a duty in the middle of mandatory rest. A second repro shows determine_tier returning tier 1 for a crew member on a week-long vacation.
Impact
Physically impossible assignments (the exact defect class D3/L0 exists to prevent) plus under-priced draft tiers, and understated occupancy in eligibility pools — all silent, all more frequent at low reserve levels where drafting is heavy. The --assert-invariants audit cannot catch the rest-overlap case (AUD-11).
Proposed fix
Make the query exact: scan for all blocks with b.start < end and b.end > start (linear over the calendar is fine at these sizes), or keep the bisect but also walk left while any block's end exceeds the query start using a precomputed running-max of end.
Verification test
Property test (hypothesis): random calendars with overlapping blocks — set(blocks_in(a,b)) == {b for b in calendar if b.start < b_end and b.end > a}; plus a regression test of the reproduced L0-during-REST case.

AUD-02 S1 CONFIRMED Sick crew are never marked unavailable — a sick pilot can be drafted, even for their own broken pairing

Outcome
FIXED Sick calls now insert an occupying ABSENCE block spanning the whole absence (both the CRN and replay paths); the reproduction’s draft selector returns the sick pilot, tier 1 no candidate, and is_legal_assignment fails on ILLEGAL_L0 for the absence window.
Location
src/crewsim/engine/sick_calls.py:56–118 (apply_sick_call/apply_named_absence), engine/des.py:361–370
Evidence
Spec §5.0.4 E1: "Remove the sick crew member's block(s) … and mark them unavailable for the absence duration" (the second clause is the surviving half of v2 defect D5). The implementation removes overlapping PAIRING blocks and stops: no absence block is inserted, and the crew member stays in self.roster. Reproduced: after apply_sick_call, is_legal_assignment returns LEGAL for the sick pilot against their own open item and select_draft_candidate picks them at tier 1 (only L8's 2 h notice masks the shortest-notice cases).
Impact
The draftable pool is overstated in every scenario that contains a sick call; multi-day absences make it worse (the pilot reads as free for days). Costs shift downward — fewer cancellations, cheaper drafts — understating the value of reserves. Emergent-eligibility and cascade rates (V3/V4 KPIs) are computed over a pool that includes the absent.
Proposed fix
Insert a SICK/ABSENCE block spanning [notification, absence_end], add it to OCCUPYING_BLOCKS, and keep it out of DUTY_BLOCKS (absence is not duty). Also decide explicitly whether reserves can fall sick (today they cannot, since only pairing-holders are sampled — a separate, documented optimism).
Verification test
Unit: after a sick call, is_legal_assignment(sick_crew, item) fails for any item overlapping the absence; scenario-level: assert no DRAFT_TIER* ledger row for a crew_id during their own absence window across a 100-scenario run.

AUD-03 S1 CONFIRMED Cool-down attribution drops in-window-caused cancellations and terminal penalties

Outcome
FIXED Every item entering the recovery pipeline books a $0 OPEN_ITEM causal marker (the spec’s own §2.3 ledger shape); the reproduced held-then-cancelled chain now attributes $0 $25,700 to the measurement window, and TERMINAL_PENALTY rows carry the item’s own uid so chains stay pairable.
Location
src/crewsim/engine/des.py:1020–1100 (rows_in_measurement_window, measured_window_costs); consumers: reporting/kpis.py:37–152, reporting/grid.py, gate V9
Evidence
Spec §5.0.5: cool-down costs are attributed to the measurement window "if their causal chain originates there". The implementation proxies a chain's origin by the earliest ledger row sharing its root_event_uid — but a sick-call arrival books no ledger row (the spec's own §2.3 example ledger has a SICK_LEAVE_PAY 0 marker row; the implementation omitted it). Reproduced with the project's own config: an item arriving on measurement day 26, held, and cancelled in cool-down contributes $0 to measured cost — the CANCELLATION + APPR rows are its first bookings, so the chain "originates" in cool-down and is excluded. The same applies to TERMINAL_PENALTY rows and to kpis.count_uncovered, which feeds the §7.5 service-level constraint.
Impact
Exactly the failure class the cool-down exists to capture is dropped. Low-R policies hold more items past the boundary, so their E[C]/CVaR₉₅/uncovered-legs are shaved hardest — the recommendation R* is biased toward fewer reserves, silently.
Proposed fix
Book a $0 marker row at item creation (matching the spec's own ledger example), or carry the root event's sim-time on OpenTimeItem and use it as the chain origin.
Verification test
Unit on rows_in_measurement_window with a chain whose only rows book in cool-down but whose root arrival is in-window (the audit's repro script is this test); integration: sum of measured costs across a scenario plus warm-up/cool-down-attributed remainder must equal the full ledger total.

AUD-04 S1 CONFIRMED Gate V4's windowed history is emptied by an epoch-seconds/datetime comparison — V4 never validated anything

Outcome
FIXED Datetime-vs-datetime window filter (also removes the machine-timezone dependence). Holdout reconstruction: 0 drafts, recall 0.000 807 drafts, rate 0.260, recall 0.902; fitting: 1,481 drafts, rate 0.261, recall 0.877. Recall’s denominator is now window-scoped, so a 12-month window is no longer condemned to ~1/3 recall by arithmetic. Live end-to-end run (20 CRN scenarios, R10): V4 renders its first real verdict — FAIL, simulated cascade rate 0.095 vs band [0.231, 0.292]. That is the gate working: a genuine model-vs-history gap is now visible and measurable where INCONCLUSIVE used to hide it. Closing it is V4's own "find the missing mechanism" work (and the reconstruction's 7-day any-event join, which over-attributes vs the manifest's 0.202, is a candidate from the other side) — model calibration work, distinct from the audit defect, which is fixed.
Location
src/crewsim/data/cascades.py:93–100 (cascade_target)
Evidence
The window filter builds start_ts/end_ts via datetime.combine(...).timestamp() (epoch seconds, local-timezone-dependent) and compares them to change_ts, a Polars datetime[μs] column. Polars interprets the float on the column's microsecond scale (~1970-01-01 00:29), so every row after 1970 fails <= end_ts. Measured in this audit: D6 has 3,105 rows spanning 2023–2026; cascade_target(window=None) reconstructs 2,289 drafts at rate 0.261, while window="holdout" and window="fitting" both return 0 drafts. The backlog's 2026-08-09 review of S1d-04 saw the symptom ("holdout recall is 0.000 — 0 of 2,584 known drafts found") and correctly added the INCONCLUSIVE verdict, but attributed it to reconstruction sparsity "outside this epic" — the actual cause is this unit error.
Impact
Gate V4 — the slice-1d exit gate — is permanently INCONCLUSIVE: the simulated cascade rate has never been compared to history. The same bug also windowed-out the recall denominator's numerator, producing the alarming-but-wrong "0 of 2,584" recall line.
Proposed fix
Compare like with like: pl.col("change_ts") >= datetime.combine(w.start, time.min) (naive datetimes, no .timestamp() — also removes the machine-timezone dependence). Then align score_recall's denominator to the same window.
Verification test
cascade_target(cfg, "holdout") must return > 0 drafts on the shipped corpus (the ground truth expects ≈ 0.88 recall); add a schema-level test that windowed row counts sum to the unwindowed count.

AUD-05 S1 CONFIRMED Calibration ignores the fitting window; the parameter store's data_window is a false claim

Outcome
FIXED The resolved fitting window is threaded through all three fitters and applied to D4/D8/D9 before any fit; the store’s data_window now describes the data the fit actually saw (regenerated store confirms 2023-08-01–2025-07-31).
Location
src/crewsim/calibration/pipeline.py:46–65; nhpp.py:21–97, regime.py:25–45, delays.py:29–49
Evidence
run_pipeline(cfg, season, window_name="fitting") resolves the window and writes it into the store's data_window metadata — but none of the three fitters receives or applies it: fit_regime spans D8's full min/max date range, fit_sick_calls uses all of D4/D9, fit_delays all of D8/D9. The fits therefore include the 12-month holdout (2025-08→2026-07). The roster template window is additionally drawn from the holdout (roster_loader.select_template_window uses windows.holdout).
Impact
§6.4's "no cheating" rule — the spec's most emphasized validation principle, and S0-09's whole purpose — is not enforced where it matters: V3 compares a simulation whose arrival process saw the holdout against a holdout reconstruction; a future V6 backtest on real data would test the model on months it was fitted on. The provenance chain (params store metadata) misstates what was fit.
Proposed fix
Thread the resolved window into each fitter and filter every frame on it (D4 absence_start, D8/D9 date); assert in the store that min/max observed dates fall inside data_window.
Verification test
Fit with window="fitting", then perturb only holdout-period rows in a copy of the corpus and refit — the content_hash must not change. Today it does.

AUD-06 S2 CONFIRMED Block equality is start-time-only; calendar removal can delete the wrong block

Outcome
FIXED Full-field frozen-dataclass equality, order=True removed (every sort already used explicit keys). The PAIRING/VACATION same-start repro now removes the wrong block exactly the named block.
Location
src/crewsim/engine/state.py:17–24; removal sites cascade.py:85–88, sick_calls.py:50–51, events.py:49
Evidence
@dataclass(frozen=True, order=True) with every field except start marked compare=False makes __eq__ compare only start. Proposed fix
Drop order=True (sorting already uses explicit keys), enable full-field equality, and prefer identity-based removal (calendar.remove is fine once equality means "same block").
Verification test
Unit: removing a PAIRING from a calendar containing a VACATION with the same start must leave the VACATION untouched.

Corpus shape defect — reserve blocks were 24h/day (2026-08-12)

Raised by the business, confirmed, fixed — and it changed the answer

A reserve is on call for a window each day (06:00–18:00), then off duty. The mock generator emitted continuous midnight-to-midnight slabs of 3–6 whole days instead. This was the root cause sitting underneath AUD-24, AUD-17 and the parked S1c-04b card.

The evidence

  • The generator used one whole-day helper for every block type. _block() computes midnight → midnight + N days, and RESERVE was passed through it exactly like DAY_OFF and VACATION. Correct for a vacation; wrong for standby.
  • The data carried no time-of-day information at all. All 5,782 reserve blocks started at hour 00 and ended at hour 00, in durations of exactly 72/96/120/144 h. Not one was a partial day.
  • The spec said the opposite. §5.0.2's reserve table lists "On call until — Tue 18:00", and §5.5 builds the whole shortest_remaining_window dispatch rule on "a reserve whose window ends at 18:00 is worth nothing after 18:00". The engine was already written for windows; only the data was wrong.
  • D5 independently showed no window. Real call-out times are flat across all 24 hours (~210/hour, every hour) — the signature of a uniform random draw, not of a daily on-call period.

What changed

RESERVE now emits one D2 row per day, each carrying that day's rostered shift, with the rotation preserved. Shifts vary — the corpus draws from a configured catalogue (morning 06:00–18:00, afternoon 14:00–02:00, night 22:00–08:00), assigned per rotation, so 17,119 of the 25,682 reserve rows legitimately cross midnight. D2 grew 185,614 → 205,887 rows as 5,782 whole-day slabs became 25,682 daily shifts.

The architecture was already right

reserve_lines is read only in config.py — no engine module consumes it. roster_loader takes each D2 row's own start_utc/end_utc verbatim, so whatever a real Air Transat extract rosters (morning, afternoon, night, varying by crew and by day) is honoured exactly as scheduled. The roster is the authority on when a reserve is on duty. The config section only shapes the mock data, and is marked [CONFIRM: Crew Planning] — replacing the catalogue with real standby shifts requires no engine change at all.

OPEN-7 — fixed, 2026-08-12

V2 had begun failing in the direction its own docstring calls impossible, instructing the reader to stop and suspect reserve double-counting. That instruction was not followed: V8's invariants — the direct calendar-level test for exactly that defect — were clean across 672 crew-scenarios, so the accusation was checked and disproved before any engine change was contemplated.

The comparison, not the engine, was broken. Two independent faults, both introduced the moment reserves became rostered shifts:

  • Mismatched currencies. Servers were counted as a time-average of on-call minutes, but service was charged as the entire duty-plus-rest span — which, since a duty may now run past the shift that authorised it, reached 19 h against 10–12 h shifts. Those out-of-shift hours remove no server capacity: the crew member was off duty and unavailable regardless. E[S] is now the on-call capacity actually consumed (10.8 h), measured before the assignment mutates the calendar.
  • Rounding decided the verdict. A rostered pool presents a fractional time-average — 7 reserves on 12 h shifts average 1.15 — and Erlang B is violently sensitive at small s: B(1, 2.06) = 0.67 against B(2, 2.06) = 0.41. round() silently picked one. Both are now computed and printed, and the gate is judged against the most generous idealisation, so a violation can only mean the DES beat even the best case. On the corrected basis the bound holds at both, so the rounding is no longer load-bearing at all.
